# 自作期待値表の作り方（段階0〜5）

実行：`python pipeline/ev/specs.py`（段階1の出典確認）→ `python pipeline/ev/run.py`（段階2〜5）。テスト：`python -m unittest discover -s tests`

| 段階 | やること | ファイル | 公開リポジトリに入れるか |
|---|---|---|---|
| 0 | 実データを集めてよいか | [data_sources.md](data_sources.md) | 入れる |
| 1 | 仕様を集める（出典URL・信頼度） | `data/specs/<ID>.yaml`、`pipeline/ev/specs.py` | 入れる（公開情報の事実だけ） |
| 2 | シミュレーション | `pipeline/ev/model.py`・`calibrate.py` → `data/ev/<ID>.json` | 結果は入れない |
| 3 | 実データで補正 | `pipeline/ev/survival.py` | コードだけ（使えるデータが無い） |
| 4 | 答え合わせ | `pipeline/ev/compare.py` → `data/compare/report.md`、[ev_status.md](ev_status.md) | 詳細は入れない（他サイトの数値を含む）。状態だけ入れる |
| 5 | note 用の表 | `pipeline/ev/tables.py` → `data/ev/tables/` | 入れない（有料の中身） |

## 段階1：仕様

- 1項目ごとに `value`（見つからなければ null）と `sources: [{url, site, evidence}]`
- `specs.py` が出典ページを開き、`evidence` の文字列が本当に書いてあるかを確かめてから、YouTube の research と同じ格付けで `confidence`（high / single / none）を付ける
- 取得対策（ボット判定など）があるサイトは回避しない。開けないページは出典として数えない

## 段階2：シミュレーション

- **型**：`game`（ゲーム数天井）／`game_cycle`（ゲーム数＋周期。周期の長さが公開されていないのでゲーム数だけ）／`cz_st`（CZ間＋ST間。CZ成功率が無いのでST間だけ）／`through`（スルー回数）／`point`（ポイント）
- **当たりやすさ**：天井まで一定。値は「天井込みの平均初当たりゲーム数＝公表の初当たり確率の逆数」になるように決める
- **AT1回の獲得枚数 A**：公表値が無ければ機械割から逆算する
  - A − N×50/C ＝ (R−1)×3×(N＋A/j)（N：平均初当たりG、C：コイン持ち、R：機械割、j：純増）
  - 逆算した A で 0G から天井まで打つと、全体の機械割（例 97.9%）に戻ることをテストで確認している
  - 逆算した A には「AT後の引き戻し・浅いゲーム数での当たりやすさ」の分も入るので、深いゲーム数から打つ人の獲得に直す係数 k を掛ける。k はメーカー公表の状況別機械割（今はリコリス・リコイルの2点）から推定（2026-10-28：k＝0.927）。**他サイトの期待値表は k の推定に使わない**（答え合わせが独立した確認でなくなるため）
- **出すもの**：開始ゲーム数ごとの期待収支（等価・5.6枚現金）・時給・平均投資・投資の90%点・天井到達率・95%信頼区間（試行回数による誤差）・推定の幅（平均獲得±5%・コイン持ち±0.5G）
- **算出条件**：`config/channel.note.yaml` の `ev:`。設定1・AT後即やめ・1時間840G（DMMぱちタウンの「1分あたり14G」）・閉店は考えない・前兆中ではない・ゾーンやモードは考えない。たられば・ちょんぼりすたの表は画像（実戦値の引用）で条件が文字になっていないため、条件が公開されている信頼サイトに合わせた

## 段階3：実データで補正

- `survival.py`：当たり履歴から「〇Gから打ったとき何Gで当たるか」を Kaplan-Meier 法で出す。閉店で終わった記録は打ち切りとして扱う（合成データのテストで、打ち切りを当たりと数えるとずれ、正しく扱うと当たることを確認）
- **今回は行っていない**：段階0で「よい」のサイトが0件、運営者の実戦記録は使わない方針のため

## 段階4：答え合わせ

- 比べる相手：なな徹の天井期待値表（算出条件が文字で公開されている信頼サイト。ちょんぼりすたの表は画像）
- 基準（結果を見る前に `ev.compare` に決めた）：比べた点の8割以上で、差が600円か相手の値の25%のどちらか大きい方の以内、かつ等価でプラスになり始めるゲーム数の差が50G以内
- 状況（通常／設定変更時など）ごとに合否を決め、不合格の状況は「準備中」。原因は `run.py` の `CAUSES` と [ev_status.md](ev_status.md)

## 段階5：表

- 合格した状況だけ、`data/ev/tables/<ID>_<状況>.md`（記事に貼る表）と `.png`（note の画像。幅1280）
- 必ず書く：「独自試算」「算出条件」「期待値は長い目で見た平均で、1回の結果を保証しない」
- 線：標準ボーダー＝狙い目シートのゲーム数（`data/sheet/_borders.yaml`。シートに行があるときだけ）、強気ボーダー＝等価でプラスになり始めるゲーム数

## 機種を増やすとき

1. `data/specs/<ID>.yaml` を書く（出典と evidence 付き。分からない項目は null）
2. `python pipeline/ev/specs.py <ID>` で確認
3. 比べる相手の表を `data/compare/raw/<ID>_nana.txt` に置き、`compare.py` の `REFERENCES` に足す
4. `python pipeline/ev/run.py <ID>`
